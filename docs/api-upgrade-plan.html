01 Current API Usage Audit

What each API does today, which endpoints are called, and which response fields are consumed.

Key gaps: Flight results discard fareSourceCode (needed for booking URLs), baggageInfo, layoverTime, and UTC offsets. Hotel results discard correlationId/token at the UI level (needed for deep-link booking), cancellationPolicy, publishedRate vs ourprice breakdown, and coordinates. No car rental or activity search is wired up.

OpenWeather Weather Data

EndpointFileFields UsedStatus

Key gaps: OPENWEATHER_API_KEY isn't set on Heroku — every request falls back to the simulated "22°C clear skies" template. Even when the API key is set, the daily[] array from One Call 3.0 (8-day forecast with high/low/condition/precip) is returned but completely ignored — only current is read. The daily aggregation endpoint (great for specific trip-date forecasts going 1.5 years ahead) is never called.

LangGraph Agent Orchestration

FeatureFileCurrent UseStatus
StateGraph + MemorySaver rootAgent.py Root → {explore, pre_travel, planning} → END Used
graph.ainvoke() rootAgent.py Synchronous wait for full result Used
graph.astream() — — (node-level streaming) Unused
graph.astream_events(v2) — — (token-level streaming) Unused
Parallel node execution — — (agents run sequentially) Unused
GPT-4o tool calling planning/agent.py Tool bindings for flight_search, hotel_search, search_restaurants, etc. Used
Structured output / response_format — — Unused

Key gaps: The entire agent pipeline runs as a single synchronous ainvoke(), with keepalive spaces masking the 30-40 second wait. LangGraph's astream() can emit after each node completes (flights done → hotels done → …), and astream_events(v2) can stream individual LLM tokens. Neither is used. Sub-agents run sequentially — flights, then hotels, then restaurants — when flights and hotels could run in parallel. GPT-4o's structured output mode (response_format) isn't used for the final itinerary, so the LLM returns markdown prose instead of typed JSON.

02 Underutilized API Capabilities

What each API can do that you're not using yet — features you're already paying for.

RouteStack Untapped Features

  • Car Rentals — /mcp/car/* endpoints for pickup/dropoff search, pricing, and booking. Already available in the API.
  • Activities & Vacation Rentals — Rolling out Q4 2026. Activities (tours, experiences) would replace or supplement Google Places for attraction recommendations.
  • Stripe ACP (Agentic Commerce Protocol) — Native in-chat payment flow announced Oct 2026. Enables real booking without leaving the app. Currently in sandbox.
  • Flight booking deep links — The fareSourceCode from search results, combined with correlationId, can generate provider booking URLs. Currently collected but never surfaced.
  • Hotel booking deep links — correlationId + token from hotel search are saved in the tool response but discarded at the UI layer. These enable direct booking flows.
  • Price breakdown fields — baseFare vs ourprice vs totalFare (flights), baseprice vs ourprice vs publishedRate + saving (hotels) — all returned, partially consumed.
  • Hotel facilities & images — Full facilities array and multiple photo URLs are returned; only the first photo and first 10 facility names are used.

Google Places Untapped Features

  • Place Details API — Never called. Provides regularOpeningHours (open on trip dates?), reviews, editorialSummary, websiteUri, internationalPhoneNumber, and richer photo arrays.
  • Nearby Search — Not used. Better for "restaurants near my hotel" than Text Search with a city name.
  • Field mask expansion — Current mask misses: priceLevel, editorialSummary, regularOpeningHours, googleMapsUri, googleMapsLinks, websiteUri, reviews, internationalPhoneNumber, addressDescriptor (new 2026).
  • Photo attribution — photos[].authorAttributions is returned but completely ignored. Google requires attribution display.
  • Photo proxy — Photo URLs currently embed the server API key: ?key={api_key}. Should be proxied server-side.
  • googleMapsLinks — Direct Google Maps links for directions, reviews, photos. Available since late 2024.
  • 180+ new place types (Feb 2026) — Filtering by specific types like historical_landmark, hiking_area, beach for better categorized recommendations.
  • Autocomplete — For destination input on the frontend, replace the current free-text to airport-code pipeline.

OpenWeather Untapped Features

  • 8-day daily forecast — Already returned in every One Call 3.0 response (daily[]), completely ignored. Each day includes temp.min, temp.max, weather[].icon, pop (precipitation probability), humidity, wind_speed, sunrise/sunset.
  • Daily Aggregation endpoint — /onecall/day_summary provides forecast or historical data for a specific date, up to 1.5 years ahead. Perfect for trip-date forecasts.
  • Historical archive — /onecall/timemachine for 47+ years of historical weather. "What was the weather in Lisbon in March historically?" — useful for packing recommendations.
  • Weather condition codes — weather[].id codes (800 = clear, 500 = rain, etc.) enable icon mapping without text parsing.
  • UV index — current.uvi and daily[].uvi for sun protection recommendations.
  • Alerts — Currently excluded (exclude=minutely,hourly,alerts). Government weather alerts for the destination could be valuable.

LangGraph Untapped Features

  • astream() — Emits state after each node completes. "Flights found → Hotels searching…" progress without keepalive hacks.
  • astream_events(v2) — Token-level streaming from inside nodes. The final narrative answer can type in word by word.
  • Parallel node execution — LangGraph supports fan-out: flight search, hotel search, restaurant search, and weather lookup can all run simultaneously, cutting total latency from ~sequential to ~longest-single-call.
  • Structured output — GPT-4o's response_format: { type: "json_schema" } guarantees the itinerary comes back as typed JSON, not markdown prose. No regex parsing needed.
  • Interrupt/resume — LangGraph's human-in-the-loop can pause the graph for clarifying questions ("Which airport? What dates?") and resume after the user answers.
  • Subgraph composition — The planning agent's internal graph could be nested as a subgraph of root, sharing state properly instead of the current manual state threading.

05 Phased Upgrade Roadmap

Suggested implementation order based on impact and dependency chains.

Phase 1 — Foundation (1–2 weeks)

Streaming + Entity Schemas + Weather Fix

  • Set OPENWEATHER_API_KEY on Heroku — Instant win. The code already calls the API; it just falls back to simulated data because the key is missing.
  • Parse daily[] from One Call 3.0 — The data is already coming back in every response. Add a function that extracts daily[].temp.min/max, weather[].id, pop, uvi and returns a typed forecast array.
  • Define entity schemas — Pydantic models for Flight, Hotel, Place, WeatherDay, Price with id, source, fetched_at, is_estimate. Normalize all tool outputs through these.
  • Switch ainvoke() → astream() in rootAgent — Emit state after each node. The SSE endpoint wraps this as event: agent and event: section messages.
  • New POST /api/llm/ask — SSE endpoint using astream(). Keep the old endpoint for compatibility.
  • Error contract — Typed error schema. SSE error events mid-stream. request_id on every response.

Phase 2 — Structured Output + Photo Proxy (1 week)

GPT-4o JSON Mode + Google Places Hardening

  • Structured itinerary output — Add response_format: { type: "json_schema" } to the planning agent's final LLM call. Define the itinerary JSON schema (trip metadata, days array, item slots with entity refs).
  • Photo proxy endpoint — GET /api/places/photo/{ref}?w=640 fetches from Google server-side, caches, returns with width, height, attribution. Stops exposing the API key.
  • Expand Places field mask — Add regularOpeningHours, priceLevel, editorialSummary, websiteUri, googleMapsUri, reviews, internationalPhoneNumber, photos.authorAttributions.
  • Extract user from bearer token — Stop accepting user_email in the request body. Read it from the Auth0 token claims.

Phase 3 — Rich Data + Conversations (1–2 weeks)

Full RouteStack Parsing + Server-Side History

  • Full flight response parsing — Extract segments with layover times, baggage info, UTC offsets, cabin class, per-traveler + total price, and booking URLs from fareSourceCode.
  • Full hotel response parsing — Extract nightly + total price, check-in/out, star rating vs guest rating, review count, amenities codes, multiple photos, cancellation policy, coordinates, and booking URLs from correlationId + token.
  • Place Details calls — After Text Search, call GET places/{id} for the top results to get opening hours, reviews, editorial summary.
  • Conversation CRUD endpoints — Server-side storage, pagination, server-generated titles, message IDs, stored structured data.
  • Cancel endpoint — DELETE /api/llm/ask/{request_id} cancels the running asyncio task.
  • Parallel agent execution — Fan out flights + hotels + restaurants + weather as parallel LangGraph nodes. Cuts total latency to ~longest-single-call.

Phase 4 — Intelligence (1 week)

Clarifying Questions + Scope Guard + Suggestions

  • LangGraph interrupt/resume — When the agent detects missing info (no origin, no dates), interrupt with a clarifying question event. Resume on user response.
  • Scope classification — Structured output to detect out-of-scope queries early. Return status: "out_of_scope" with helpful redirects instead of refusals.
  • Follow-up suggestions — Add suggestions[] to every response: "Add a Sintra day trip", "Cheaper hotels", "Show weather for those dates".
  • Token-level streaming — Upgrade from astream() to astream_events(v2) for the narrative answer portion. The itinerary text types in word by word.
  • Destination geocode + map bounds — Return viewport from the destination's Places result as the first SSE event, so the map centers before results arrive.

Phase 5 — Scale & Delight (2+ weeks)

Preferences, Sharing, Bookmarks, New Inventory

  • User preferences — Locale, currency, units, home airport, traveler defaults. Pass to RouteStack, OpenWeather, and display logic.
  • Feedback endpoint — POST /api/feedback with message_id, rating, reason.
  • Saved places / bookmarks — Powers the "Saved" nav item (currently "Soon").
  • Export — .ics calendar export from the structured itinerary. PDF via server-side rendering.
  • Read-only share links — Generate a public link for a completed itinerary.
  • Car rental integration — Wire up RouteStack /mcp/car/* endpoints.
  • Activities integration — When RouteStack rolls out activities in Q4, integrate as an alternative to Google Places for experience-type recommendations.
  • Performance targets — gzip/brotli compression, popular destination cache, first SSE event <1s, first section <8s, p95 total <30s.
  • OpenAPI spec — Auto-generate from FastAPI with schema_version field. Fixture responses for every state.
